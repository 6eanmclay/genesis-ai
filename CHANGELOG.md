# Changelog

Notable architecture, security, and data-model changes to Genesis AI, organized by [engineering roadmap](https://claude.ai/code/artifact/7679e3e9-1030-4d2b-b3b4-9a18fd64b4a7) phase. Routine content/copy/prompt tuning isn't logged here — this tracks the decisions a future developer (or future us) would need to understand *why* the system is shaped the way it is.

For what the system currently looks like (not chronological), see [ARCHITECTURE.md](./ARCHITECTURE.md).

## Phase 0 — Foundation
*2026-07-18 – 2026-07-22, before the structured roadmap existed*

Condensed summary — this predates phase-by-phase tracking, so it's one entry covering everything that shipped before PH-01.

**What was built**
- Auth: email/password (bcrypt) + Google OAuth, NextAuth v5 (JWT sessions), `session.user.id` via custom callbacks.
- AI store generation: Anthropic Claude (`claude-opus-4-8`) generates a full brand identity, homepage content, theme, and product catalog from a plain-English description. Structured outputs via Zod schemas.
- Genesis conversational assistant: multi-turn chat for both the pre-launch draft and (added later) the live store, with programmatically-computed diffs (not AI self-report) driving the visible "what changed" log.
- Public storefront: AI-chosen homepage section order, brand-driven visual presentation (card/button/shadow/spacing style derived from brand personality, not just color), individual product detail pages, real placeholder images via the Unsplash API.
- Stripe Checkout: single-item purchase flow, webhook-driven `Order` creation.
- Production deployment: Vercel + Neon Postgres.

**Database migrations**
- Initial schema: `User`, `Account`, `Session`, `Store`, `Product`, `Order`, plus the AI-generation support tables (`StoreDraft`, `StoreGeneration`, `StoreDraftMessage`, `StoreMessage`), `NewsletterSignup`.

**Verification performed**
- Manual end-to-end testing throughout (signup/login, store generation, checkout with real Stripe test-mode purchases, production deployment smoke tests).

## PH-01 — Permissions & Security
*2026-07-23 — Complete*

**What was built**
- A real role system: Owner, Employee, extensible for future roles. Customer is *not* a stored role — it's the absence of ownership or membership, which the system now actively enforces rather than accidentally getting right.
- `lib/permissions.ts`: a single authorization chokepoint (`requireStorePermission`) that every protected route, server action, and (per explicit design requirement) Genesis-driven AI action now goes through, replacing 8 previously scattered hand-rolled ownership checks.

**Architecture decisions**
- `Store.userId` stays the owner, unchanged — a new `StoreMember` table (`storeId`, `userId`, `role`) handles non-owner access only. Zero migration risk to existing single-owner data or flows.
- Permissions are capability strings (`PERMISSIONS.PRODUCTS_MANAGE`, etc.) mapped from role via a `ROLE_PERMISSIONS` table, not scattered `role === "OWNER"` comparisons — chosen so a future move to per-user permission overrides is additive, not a rewrite of every call site.
- Two permissions (`ANALYTICS_VIEW`, `PAYMENTS_MANAGE`) were reserved with no code using them yet, specifically so later phases (PAYMENTS_MANAGE ended up used the very next day, in PH-02) only need to wire an existing permission into a new action.
- **Genesis chat enforces the same permission model as manual actions** — not something I originated, the user's explicit requirement during design. Since every current Genesis capability for a live store is `STORE_MANAGE`-shaped, an Employee can open the chat but any request is declined *before* calling Claude at all — both to avoid burning a generation on a foregone conclusion, and to guarantee Genesis can never claim a change happened when it didn't.

**Database migrations**
- `add_store_members`: new `StoreRole` enum (`OWNER`, `EMPLOYEE`), new `StoreMember` model.

**Breaking changes**
- None. Existing single-owner flows were verified unaffected.

**Verification performed**
- 17 direct checks against live data (`getStoreRole`/`hasPermission`/`resolveUserStore`) — all passed.
- Real cookie-based sessions (through NextAuth's actual credentials callback, not mocked) as three fresh test accounts: a dedicated Owner (full access), an Employee attached to a real existing store (Products/Orders/Genesis chat visible, Store settings/Publish correctly absent), and a fully unaffiliated user (empty "Create your store" state, zero trace of any real store).
- Test fixtures created fresh rather than touching existing accounts, after an earlier incident that session where a verification script auto-deleted real test data — see the "never auto-delete existing account data" rule this incident produced.

## PH-02 — Integration Framework
*2026-07-23 — Complete*

**What was built**
- A generic connector contract (`lib/integrations/types.ts`) every external integration implements: `connect`, `verify`, `disconnect`, `status`. Stripe (`lib/integrations/stripe.ts`) is the first, reference implementation — not a special case the framework was built around.
- `lib/integrations/registry.ts`: provider → connector lookup, so callers never hardcode which provider they're talking to.
- Real Stripe Connect OAuth (Standard accounts) — explicitly chosen over merchants pasting API keys. User's reasoning: "Genesis is a multi-merchant platform, I'd rather establish the correct architecture now than build something we'll replace later."
- One generic OAuth callback route (`app/api/integrations/[provider]/callback/route.ts`) serves any current or future OAuth-style provider.
- `createCheckoutSession` now resolves a per-store Stripe client from the store's connection when one exists, falling back to the original platform-wide key when it doesn't — so none of the stores already live break on rollout.
- A minimal "Payments" section on the dashboard (Owner-only) for Connect/Reconnect/Disconnect/Recheck.

**Architecture decisions**
- `StoreIntegration` is one generic table for every provider (`provider`/`status` enums, opaque `credentials` Json, `connectedByUserId`/`connectedAt` audit fields) — not one table per integration. Enums instead of raw strings and the audit fields were both added per explicit user request during design.
- The connector contract is deliberately generalized beyond OAuth: `connect()` returns a `ConnectResult` union (`redirect` for OAuth-style, `form` for a future API-key-style provider like USPS, `connected` when done in one step) so the framework never assumes *how* a connector authenticates — also per explicit user request, to avoid boxing in providers that don't use OAuth.
- "Monitor" (from the Connect → Authenticate → Verify → Monitor → Reconnect lifecycle) is implemented as "verifiable on demand" for now, not a background scheduler — no job/cron infrastructure exists in this app yet, and building one wasn't in scope here. A real health-score presentation (🟢/🟡/🔴, consecutive failures, recommended action) is deliberately deferred to PH-03, which is where that kind of operational visibility belongs.

**Security improvements**
- The webhook handler no longer trusts `session.metadata.storeId` for connected-account events. A connected merchant's OAuth access token is usable as their own full Stripe API key, so a malicious merchant could call the Stripe API directly with fabricated metadata claiming a *different* store's ID, attempting to inject fake orders. Fixed by trusting `event.account` (set by Stripe itself, not forgeable via metadata) as the source of truth for connected-account events, resolved to a store via `StoreIntegration.externalAccountId`; metadata is only trusted for platform-key events, which the app controls end-to-end. Found and fixed during implementation, not called out explicitly in the approved design.

**Database migrations**
- `add_store_integrations`: new `IntegrationProvider` enum (`STRIPE`, `PAYPAL`, `GOOGLE`, `SLACK`, `USPS`), new `IntegrationStatus` enum (`CONNECTED`, `NEEDS_ATTENTION`, `FAILED`, `DISCONNECTED`), new `StoreIntegration` model.

**Breaking changes**
- None. The platform-key fallback was specifically designed and verified so existing checkout behavior is unaffected until a store owner actively connects their own account.

**Verification performed**
- Confirmed against the live Stripe API: a store with no connection still creates a genuine checkout session via the fallback path; once a `CONNECTED` integration exists, resolution correctly switches to a different client.
- Confirmed `PAYMENTS_MANAGE` gating via real cookie sessions (reusing the PH-01 fixtures, not creating new ones): Employee sees zero trace of the Payments section, Owner sees it in full.
- **Full Stripe Connect OAuth round-trip, run for real against the live Stripe API**, once `STRIPE_CONNECT_CLIENT_ID` was configured: connected a real test-mode Stripe account to Lunar Mothworks via the actual Connect button → `StoreIntegration` row created with `status: CONNECTED` and correct `connectedByUserId`/`connectedAt`. Made a real test-mode purchase on the storefront and confirmed, via direct Stripe API calls, that the resulting Checkout Session exists **only** on the connected account (`acct_1TwCG2BWLquB34sx`) and does **not** exist on the platform account — money genuinely lands with the merchant, not Genesis. Set up the Stripe CLI (`stripe listen`) to forward webhook events to the local dev server, made another real purchase, and confirmed the `checkout.session.completed` webhook (correctly tagged as a `connect` event) resolved via `event.account` to the correct store and created an `Order` row with the right product/amount/store.

**Bugs found and fixed during this final verification pass**
- The OAuth callback route (`app/api/integrations/[provider]/callback/route.ts`) was silently swallowing connector errors in a bare `catch {}`, showing only a generic "Couldn't connect Stripe" with nothing in the server logs — made real debugging impossible. Fixed by logging the underlying error (`console.error`) before redirecting, which is what actually surfaced the next issue below. This should have logged from the start; a caught error with no logging is a real gap, not intentional error-hiding.
- The first two real connect attempts failed with Stripe's `invalid_grant` error ("Authorization code provided does not belong to you") because `STRIPE_SECRET_KEY` in `.env` belonged to a different Stripe account (`acct_1TuhvRBDW1ilB8Vd`, "Genesis") than the one where Connect/OAuth was actually configured (`acct_1TuhvbBo3H6St4fl`, "Genesis sandbox") — an environment misconfiguration outside the app's code, caught by testing against the real API rather than assumed to be a code bug. Fixed by pointing `STRIPE_SECRET_KEY` at the correct account's test-mode secret key.

## PH-03 — Execution & Verification Engine
*2026-07-23 — Complete*

**What was built**
- A universal action lifecycle (Request → Execute → Verify → Record Result → Display Status → Offer Recovery), reframed mid-design from a narrow integration-only "Verification Engine" per explicit user direction: any action Genesis or a merchant performs can now report through one standardized `ExecutionResult` shape instead of inventing its own success/failure handling.
- `lib/execution/`: `types.ts` (`ExecutionResult`, `ExecutionStatus`, `ActorType`), `executable.ts` (`Executable` contract), `engine.ts` (`execute()` — the single place a retrofitted action's outcome flows through), `actions.ts` (`EXECUTION_ACTIONS` registry, same pattern as PH-01's `PERMISSIONS`), `log.ts` (`recordExecution()`, the only place `ExecutionLog` gets written), `genesis.ts` (the lightweight Genesis logging hook), `adapters/integrationExecutable.ts` (adapts PH-02's `IntegrationConnector` into `Executable`), `executables/storePublish.ts`.
- Two real proof-of-concept retrofits, matching the original narrower phase's scope: `toggleStorePublished` and Stripe `connect`/`verify` (`app/dashboard/actions.ts`) now route through `execute()`. This directly fixed a live bug: `recheckStripe()` previously discarded Stripe's `{ok, error}` verification result entirely — it's now persisted and actually displayed.
- A lightweight Genesis logging hook (not a refactor): `applyGenesisMessage`/`applyGenesisMessageToStore` (`app/dashboard/ai-actions.ts`) keep their tuned two-call generation flow, diff tracking, and confirmation logic completely unchanged, but now each write one `ExecutionLog` row (`actorType: GENESIS`) after finishing — applied, declined, pending-confirmation, or failed — so AI-driven actions appear in the same unified history as human-triggered ones.
- `ExecutionStatusCard` (`app/dashboard/ExecutionStatusCard.tsx`): a small reusable status-display component (colored dot + message + verified/timestamp), replacing the dashboard's ad hoc Stripe status derivation and the ephemeral query-string success/error banners.

**Architecture decisions**
- **`ExecutionLog` is append-only — a row is never updated after insert.** A logical request's status changing over time (e.g. an OAuth handoff going `PENDING` → `SUCCESS`) is a new row sharing one `executionId` (a fresh UUID per logical request), not a mutated row. Added per explicit user feedback on the design ("execution history is an audit log — you don't want history changing"). Enforced this phase as a coding convention: `lib/execution/log.ts` only ever calls `.create()`.
- **`executionId` groups related rows without forcing them together.** The Stripe OAuth handoff's `PENDING` row (written when Connect starts) and its resolution row (written by the callback route) share one `executionId` via a best-effort lookup — the callback route finds the most recent `PENDING` row for the same `(storeId, action)` and reuses its id, rather than encoding it into Stripe's own OAuth `state` param, which would have meant touching PH-02's already-verified, real-money-tested authorize-URL logic. `lib/integrations/stripe.ts` and `registry.ts` have zero diffs from this phase — confirmed via `git diff --stat`.
- **`schemaVersion` added to `ExecutionResult` and `ExecutionLog`**, per explicit user feedback — `metadata`'s shape will inevitably change per-action over time; a version number lets future code interpret older rows correctly instead of assuming today's shape forever.
- **`action` is a plain `String`, not a Postgres enum** — same open-ended-vocabulary reasoning as `StoreMessage.role`. `IntegrationProvider` is a closed enum because providers are added rarely and deliberately; the action catalog grows with every feature phase, and an enum would force a schema migration for each one.
- **`verified` stays a separate boolean from `status`** — a write succeeding (`SUCCESS`) is not the same epistemic claim as independently confirming it stuck (only Stripe's `verify()` does this today). This is the infrastructure-level expression of the existing conversational-quality principle: never conflate "we tried" with "we confirmed."
- **`IntegrationConnector` (PH-02) and `Executable` (PH-03) stay separate contracts, composed via a thin adapter** rather than folded into one — `ConnectResult`'s `redirect`/`form`/`connected` cases don't map cleanly onto a single `run()` call, and forcing them to would bloat `Executable` with integration-only concepts.
- **Genesis's own AI-driven actions are explicitly NOT refactored onto the engine this phase** — a deliberate scope decision, made with the user, to prove the engine on two real human-triggered cases first (mirroring PH-02's "retrofit Stripe as proof-of-concept, not abstract design" precedent) before touching the carefully-tuned generation/diff pipeline. `execute()` takes `actorType` as an explicit parameter specifically so a future full Genesis retrofit is possible with zero engine changes.
- **`ExecutionLog.storeId`/`storeDraftId` are both optional** — found during implementation, not anticipated in the original design: Genesis's draft-side chat (`applyGenesisMessage`) happens before a `Store` row exists, only a `StoreDraft`. Mirrors the exact dual-phase pattern `StoreGeneration` already established.

**Bugs found and fixed during implementation**
- The engine's `try/catch` around `requireStorePermission` would have silently swallowed Next.js's internal `redirect("/login")` error into a `FAILED` result instead of letting the actual redirect happen, breaking the existing unauthenticated-user experience. Fixed with `unstable_rethrow(error)` at the top of both catch blocks (confirmed via `node_modules/next/dist/docs`: "redirect should be called outside the try block... redirect throws an error so it should be called outside the try block").
- `recheckStripe()`'s discarded verification result (see PH-02 above) — fixed as part of this phase's own retrofit, not a separate fix.

**Database migrations**
- `add_execution_log`: new `ExecutionLog` model.
- `execution_log_optional_store_draft`: `ExecutionLog.storeId` made optional, `storeDraftId` added — found necessary during implementation (see above).

**Breaking changes**
- None. Every retrofitted action's existing behavior (redirects, thrown errors, permission gating) is unchanged from the outside — `execute()` wraps the existing logic rather than replacing its contract with callers.

**Verification performed**
- `npx tsc --noEmit` / `npx eslint` clean on every touched/new file.
- Real cookie-session HTTP tests (posting actual no-JS-compatible Server Action form submissions, extracting the real `$ACTION_ID_...` field from rendered HTML — same rigor as PH-01/PH-02, not simulated): toggled store publish as Owner → correct `SUCCESS` `ExecutionLog` row with accurate metadata. Clicked Connect Stripe as Owner → correct `PENDING` row with the real Stripe authorize URL as the redirect target. Sent a Genesis message as an Employee lacking `STORE_MANAGE` on Lunar Mothworks → confirmed the existing decline behavior is byte-for-byte unchanged AND now produces a `WARNING` `ExecutionLog` row; confirmed the store's real data was untouched. Sent a real Genesis chat message as an Owner (a genuine Claude API call, not mocked) → confirmed a `SUCCESS` row with `metadata.changes` matching the actual diff, and confirmed the store's tagline genuinely changed.
- Directly verified the append-only/`executionId`-linkage design: confirmed no `.update()`/`.upsert()` calls exist anywhere on `ExecutionLog` in the codebase (grep), and confirmed the callback route's PENDING-row lookup query correctly resolves to the right `executionId`.
- Confirmed the pre-PH-03 compatibility fallback: simulated Lunar Mothworks' exact real state (a `CONNECTED` `StoreIntegration` with zero `ExecutionLog` rows, since its connection predates this phase) on a test fixture and confirmed the dashboard renders the correct green "Connected" card from `StoreIntegration`'s own fields — Lunar Mothworks' real owner will see this exact same correct rendering without needing to reconnect.
- Confirmed `lib/integrations/stripe.ts`/`registry.ts` and `app/store/[slug]/actions.ts`/the webhook route have zero diffs from this phase.

## PH-05 — Owner Dashboard
*2026-07-23 — Complete*

**What was built**
- Reframed from a "reporting dashboard" to a decision dashboard, per explicit user direction: every new section answers one of three questions — **What happened? What needs attention? What should I do next?** — with `ExecutionLog` (PH-03) as the structural backbone.
- Retrofitted the remaining store-management CRUD actions onto `execute()`: `createProduct`, `editProduct`, `deleteProduct`, `toggleProductActive`, `editStore` (`lib/execution/executables/{products,storeEdit}.ts`) — so the Activity Feed reflects a merchant's actual day-to-day work, not just publish/Stripe/Genesis events. Deliberately bounded scope: storefront actions (`createCheckoutSession`, `subscribeToNewsletter`) and the Stripe webhook were explicitly left untouched.
- `lib/dashboard/`: `whatHappened.ts` (`getOrderSummary`, `getRecentActivity`), `needsAttention.ts` (`getRecentNegativeOutcomes`, `getStaleExecutions`, `getIntegrationIssues`, `getStateIssues`, `getAttentionItems`), `recommendations.ts` (producer-pattern `getRecommendations`), `customers.ts` (`getCustomerSummaries`, derived from `Order.buyerEmail`), `inventory.ts` (`getInventorySnapshot`, an honest active/inactive count substitute — no `Product.stockQuantity` invented).
- New dashboard components: `ActivityFeed`, `AttentionPanel`, `RecommendationsPanel`, `OrderSummaryCard`, `CustomersList`, `InventorySnapshotCard`. `lib/execution/statusDisplay.ts` extracted so multiple components share one status→color mapping.
- First real wiring of `ORDERS_VIEW`/`REVENUE_VIEW`/`ANALYTICS_VIEW` (reserved since PH-01, unused until now).

**Architecture decisions**
- **Recommendations use a producer pattern, not a single function** — `RecommendationProducer { name, produce(ctx) }`, each pure (never sees another producer's output), merged/deduped/sorted only by `getRecommendations()`. One producer ships this phase (`ruleBasedProducer`, deterministic heuristics over already-computed data, zero added latency/cost). PH-07's Genesis-generated producer is a new array entry, not a rewrite. `Recommendation.id` is stable (e.g. `recommend.publish_store`) specifically to support future dismiss/track/dedupe — added per explicit user feedback on the design.
- **Orders are surfaced by querying `Order` directly, not by adding checkout events to `ExecutionLog`** — an explicit, deliberate scope boundary from the user: the webhook stays untouched this phase. `getOrderSummary`/`getCustomerSummaries` read `Order` directly; the Activity Feed only ever reflects store-management actions and integration/Genesis events.
- **Activity Feed and Attention Panel are gated `STORE_MANAGE` (Owner-only) this phase, not architecturally permanent** — since the feed mixes in action types (Stripe changes, store renames) an Employee has no visibility into anywhere else on the dashboard. `ActivityItem.action` already carries enough to filter by row type later (e.g. show `product.*` to `PRODUCTS_MANAGE` holders while hiding `integration.*`) without a schema or query change — noted per user feedback, not built now.
- **Two-source "What needs attention," never blended**: recent negative outcomes (`FAILED`/`WARNING` `ExecutionLog` rows, 7-day window) and stale `PENDING` handoffs (>1hr old, correctly excluding rows later resolved under the same `executionId` — respects the append-only design) are timestamped "Recent issues"; direct business-state checks (unpublished, zero active products, no payment method) are untimestamped "Needs fixing now." Rendered as two distinct groups, never merged into one list.
- **Layout order is Attention → Recommendations → Activity → Business snapshot**, not a data-source reading order — urgency before history, per explicit user feedback: people address problems, then decide what to do, then review history, then check the broader picture.
- **Inventory stays an honest substitute** (active/inactive product counts) — no `Product.stockQuantity` invented. Confirmed by the user as the right kind of discipline: expose what the schema actually knows rather than imply inventory management that doesn't exist.
- **Noted, not built**: `ExecutionLog.executionId` already groups rows from one logical request (e.g. a single Genesis turn touching homepage/theme/logo together) — a future Activity Feed could collapse same-`executionId` rows into one line instead of listing each field separately. The current design doesn't block this; it's a pure transform over `getRecentActivity`'s existing return shape.

**Bugs found and fixed during implementation**
- **PH-03's `engine.ts` writes the final `actorType` from an outer `opts.actorType ?? "USER"` constant, never from `ctx.actorType`** (which is correctly `"SYSTEM"` for `requiredPermission: null` executables but never read again). Zero live impact today (no `requiredPermission: null` executable exists), so left unfixed deliberately to keep PH-05's touch-surface disciplined — documented in `ARCHITECTURE.md` for whoever builds the first one (likely PH-06's PayPal webhook).
- **Prisma's `groupBy`/`aggregate` reject a present-but-`undefined` `_sum` key** (`"needs at least one truthy value"`) — different from omitting the key entirely. `getOrderSummary`/`getCustomerSummaries` initially built this conditionally via a ternary, which also confused TypeScript's return-type inference across the resulting union-typed args object. Fixed by writing fully separate `if (includeRevenue)`/else branches with literal args objects in both functions, found via a real 500 error hit while testing the Employee dashboard view (not caught by `tsc`/`eslint` alone — a live request was needed).

**Database migrations**
- None. `Order` and `ExecutionLog` already carried every field this phase needed.

**Breaking changes**
- None. All five retrofitted CRUD actions keep identical external behavior (redirects, validation errors) — `execute()` wraps existing logic without changing callers' contract.

**Verification performed**
- `npx tsc --noEmit` / `npx eslint` clean on every touched/new file.
- Real cookie-session HTTP tests, including `.bind()`-based Server Actions (a new encoding pattern not seen in earlier phases — three hidden fields, `$ACTION_REF_N`/`$ACTION_N:0`/`$ACTION_N:1`, extracted and resubmitted with real bound arguments): `editStore`, `createProduct`, `toggleProductActive`, and `deleteProduct` all confirmed to produce correct `ExecutionLog` rows (`store.edit`, `product.create`, `product.toggle_active`, `product.delete`) with accurate metadata, and confirmed the real underlying data (`Store.description`, the created/toggled/deleted `Product` row) changed correctly.
- Confirmed permission gating with real sessions: Owner sees all four new sections plus revenue figures; Employee (`ORDERS_VIEW`+`PRODUCTS_MANAGE`+`GENESIS_CHAT`, no `STORE_MANAGE`/`REVENUE_VIEW`/`ANALYTICS_VIEW`) sees Business Snapshot and Customers with counts only (no dollar figures, no "in revenue" text anywhere in the response), and does not see Attention Panel, Recommendations, or Activity Feed at all.
- Confirmed via direct DB query: real `Order` aggregates for Lunar Mothworks (1 order, $9.99) match what `getOrderSummary` computes; zero `ExecutionLog` rows exist with `action: "order.created"`, confirming the webhook was genuinely left untouched per the phase's explicit scope boundary.

## PH-06 — Payment Providers: PayPal
*2026-07-23/24 — Complete*

**What was built**
- The second connector on PH-02's Integration Framework, and the first to use simple per-merchant API credentials (`lib/integrations/paypal.ts`) instead of OAuth — each merchant creates their own PayPal Developer app and enters its Client ID/Secret via `ConnectResult`'s `{kind: "form"}` branch, designed in PH-02 for exactly this case but never exercised by a real connector until now.
- `lib/payments/router.ts`'s `selectProvider()` — the one place checkout-provider policy lives (prefer Stripe, then PayPal, then the platform-wide Stripe fallback), so a third/fourth provider later means one new case here, not re-touching checkout.
- `Order.stripeSessionId` renamed to a provider-agnostic `externalOrderId` + new `paymentProvider` column, composite-unique together — migration hand-written (not Prisma's naive diff, which would have dropped real order data) to preserve existing rows.
- PayPal checkout + synchronous capture (`app/api/checkout/paypal/return/route.ts`) — no webhook this phase (see Architecture decisions).
- New dashboard UI: a "Connect PayPal" → credentials form → connected-status flow, mirroring Stripe's section but with a genuinely new second-step shape (`submitPaypalCredentials`) since there's no OAuth callback route to play that role for a form-based connector.
- Bundled, disciplined PH-04 (API Architecture) cleanup: fixed a real bug in PH-03's `engine.ts` (`actorType` was read from the wrong variable), extracted shared connector utilities (`lib/integrations/util.ts`) out of `stripe.ts`, added an "API design conventions" note to `ARCHITECTURE.md` documenting patterns already in real use.
- A real engine generalization found during this phase's design, not anticipated in PH-03: `Executable.run()` gained a `pending?: boolean` outcome field (alongside the existing `redirectUrl`) so a form-based connect's first call — which completes nothing, just discovers what input is needed — is correctly `PENDING`, not incorrectly `SUCCESS`.

**Architecture decisions**
- **Per-merchant credentials over PayPal's Partner/Connect OAuth**, decided explicitly with the user: the latter would mirror Stripe Connect's one-click experience more closely, but requires PayPal to enable the platform as a "Partner" first — an external, non-instant approval unlike Stripe Connect's self-serve setup — and is a meaningfully bigger build than this phase's sizing supports. Proving the framework's non-OAuth branch works with a real provider was judged the more valuable test of "the framework generalizes" than a second OAuth-flavored connector.
- **Credential versioning** (`schemaVersion: 1` inside every connector's stored `credentials` Json, both PayPal's and — retrofitted for consistency — Stripe's) added per explicit user feedback on the design: cheap now, avoids an intractable multi-shape-credentials problem the day a provider's required fields change.
- **Provider selection centralized in `lib/payments/router.ts`**, not embedded as `if (stripe) ... else if (paypal) ...` inside checkout — added per explicit user feedback: a small dedicated module means adding Square/Authorize.net/Apple Pay/Google Pay later is one new case, not a re-touch of checkout every time.
- **No PayPal webhook this phase, capture is synchronous** on the buyer's return from approval. A real webhook isn't just "add signature verification" — each merchant's own PayPal app needs its own webhook subscription (a `webhook_id`), which would mean a *fourth* credential field through the dashboard form: genuine scope growth, not a small addition. Synchronous capture-on-return is the authoritative payment-completion signal for this flow with no dependency on webhook delivery timing at all — arguably more robust than Stripe's current flow (where the `Order` row is only ever written by webhook delivery), not a lesser version of it. Idempotency: a double-hit on the return route (back button, reload) → PayPal's `422 ORDER_ALREADY_CAPTURED` → treated as success, same posture as the Stripe webhook's no-op redelivery.
- **Checkout provider chooser UI deferred**, deterministic policy shipped instead — the original roadmap criterion implied a visual chooser; with only two providers live, that's a clean low-risk follow-up, not something to cram into this phase alongside a schema migration, a new connector, and a new capture flow.

**Bugs found and fixed during implementation**
- **PH-03's `engine.ts` `actorType` bug**, documented as a known issue during PH-05, fixed now: the final `actorType` on every `ExecutionResult` came from the outer `opts.actorType ?? "USER"` constant, never `ctx.actorType`. Zero live impact on any PH-01–05 caller (all had `requiredPermission` set); fixed on principle while touching this file anyway, not because PayPal ended up needing it (it didn't — no PayPal webhook was built).
- **A real gap found during this phase's own verification, not anticipated in the plan**: the dashboard's PayPal section, copied from Stripe's `latestStripeLog` pattern, gated the `ExecutionLog` query on a `StoreIntegration` row already existing — but PayPal's form-stage log row exists *before* any `StoreIntegration` row does (that only gets created once credentials are actually submitted and validated), so the credentials form silently never rendered. Caught by directly testing the real flow with cookie sessions, not by code review; fixed by removing that gate for PayPal's query specifically.
- **A UX gap found during the same verification pass**: after a failed connect attempt (invalid credentials) with no prior successful connection, the dashboard silently reverted to the plain "Connect PayPal" button with no indication the last attempt failed — the failure was correctly recorded in `ExecutionLog` but never surfaced. Fixed by showing the last attempt's error message inline above the button when the most recent log is `FAILED`.

## PH-07, Layer 2 — AI Explanations of Rule-Based Recommendations
*2026-07-24 — Complete*

First AI layer of PH-07, per the user's explicit staged rollout plan (rule-based → AI *explains* → AI *generates* → AI *acts with approval*). This layer adds Genesis narrating *why* an existing rule-based recommendation matters, without deciding *what* to recommend — layers 3 and 4 remain future work.

**What was built**
- `RECOMMENDATION_MESSAGES` (`lib/dashboard/recommendations.ts`): the 6 rule-based recommendation strings extracted into one exported map, keyed by the existing stable `Recommendation.id`. `ruleBasedProducer` now reads from this map instead of duplicating literals, so it and the new explanation service can never drift apart.
- `lib/dashboard/explainRecommendation.ts`: `getRecommendationExplanation({recommendationId, storeId?, storeName})` — a single reusable service, the first minimal-schema Anthropic call in the codebase (`z.object({explanation: z.string()})`, one field) and deliberately lighter-weight than every existing call in `ai-actions.ts` (`max_tokens: 1024`, `output_config.effort: "low"` vs. the uniform `16000`/`"high"` used everywhere else — a short explanation doesn't need blueprint-scale budget). Resolves the message to explain itself from `RECOMMENDATION_MESSAGES`, so a client can never pass in what gets explained — only which known id to explain. Throws on an unrecognized id (a real error, not silently swallowed) and on a failed/unparsed API response.
- `explainRecommendation` server action (`app/dashboard/ai-actions.ts`): re-checks `PERMISSIONS.ANALYTICS_VIEW` server-side, then delegates to the service. Called directly as an async function from a Client Component (not `<form action>`), so its typed return renders inline without a page navigation. No `ExecutionLog` row — not a mutation with an outcome to verify, closer to a chat reply than an executed action.
- `RecommendationItem.tsx` (new, replaces the earlier `RecommendationExplainButton.tsx` after a same-day design revision — see below): owns each recommendation's full row markup so a single component can drive both a trigger button in the action column and the resulting explanation text under the message from shared per-item state.

**Architecture decisions**
- **Deliberately not a second `RecommendationProducer`.** PH-05's producer-purity rule (`produce()` only ever sees `RecommendationContext`, never another producer's output) exists for *independent* recommendation generation. Explaining an already-decided recommendation is a transformation over existing output, not a new proposal — implementing it as a producer would misuse a pattern built for something else. It's a standalone, on-demand enrichment step entirely outside `getRecommendations()`.
- **On-demand, not eager, and not persisted/cached** — both explicit user decisions during design. Recommendations keep rendering instantly from the rule-based producer; a Genesis call only happens when a merchant actually clicks. No caching this phase, but `getRecommendationExplanation` is a single pure function specifically so a caching layer can wrap it later without touching the server action, the UI, or any call site.
- **The service resolves its own message server-side from a stable id, not a client-passed string** — per explicit user feedback on the initial design, so the client can never influence *what* gets explained beyond selecting a known recommendation id.
- **An explicit "don't propose new recommendations" guardrail is in the system prompt** — per explicit user feedback: this call must only narrate the given recommendation, never become a backdoor way to get fresh suggestions outside the rule-based producer, which would blur the "narrate why, don't decide what" boundary this layer exists to hold.
- **Return value is a typed `RecommendationExplanation` object, not a bare string** — per explicit user feedback, leaving room for future fields (e.g. a generation timestamp) without a signature change at any call site.
- **Same-day UX revision, made after the user's own live test**: the button initially rendered as a small underlined text link nested under the recommendation's message, which the user found easy to overlook entirely during testing. Restyled as a solid pill button ("✨ Ask Genesis") using the same `var(--brand-accent, var(--foreground))` treatment as the existing Genesis chat launcher/submit button, moved into the action column alongside the recommendation's own `actionLabel` link (e.g. "Connect Stripe") rather than under the message. This required promoting the per-item explain logic from a small button-only component into `RecommendationItem.tsx`, which owns the entire row so state can drive both the button's position (action column) and the resulting explanation text's position (under the message) independently.

**Verification performed**

- Direct service-level verification (bypassing HTTP — see note below): two real Claude API calls for different recommendation ids each produced a genuine, distinct explanation that added business-impact reasoning without restating the recommendation's own wording or proposing anything new; an unrecognized recommendation id correctly threw `Unknown recommendation id: ...`.

## PH-07, Layer 3 — AI-Generated Recommendations
*2026-07-24 — Complete*

Third AI layer of PH-07: Genesis stops only narrating pre-decided rules (Layer 2) and starts proposing its own recommendations from the store's real business data. Layer 4 (AI acting on recommendations with approval) remains future work — this phase only proposes, never executes.

**What was built**
- New `GeneratedRecommendation` table — AI-generated recommendations are persisted and read from cache on every dashboard load (a cheap indexed DB read, not an AI call), preserving Layer 2's latency/cost discipline. An explicit "✨ Ask Genesis to Review My Business" button (`reviewBusinessWithGenesis` in `app/dashboard/ai-actions.ts`) triggers regeneration; a "Generated X ago" timestamp shows freshness. No automatic/background regeneration this phase.
- `lib/dashboard/generateGenesisRecommendations.ts`: the Claude-calling generation service. Fetches rich business context itself (brand identity/voice, real product catalog with names/prices, customer summaries, inventory snapshot, recent activity) — all data already fetched elsewhere on every dashboard load for the Owner, so this is zero new queries, only a larger prompt. Output is a bounded, constrained Zod schema (`max(4)` recommendations, `actionHref` restricted to the four real in-page anchors, no free-form links). Persists via an atomic transaction that replaces the store's entire prior batch, and logs the full generated batch into `ExecutionLog.metadata` via `recordGenesisExecution()` (new `EXECUTION_ACTIONS.GENESIS_RECOMMENDATIONS_GENERATE`).
- `genesisProducer` (`lib/dashboard/recommendations.ts`): a second `RecommendationProducer` that only ever reads the cached `GeneratedRecommendation` rows — never calls Claude itself, so it's safe to run on every `getRecommendations()` invocation exactly like `ruleBasedProducer`. Both producers are now the default (`getRecommendations`'s default `producers` array).
- `RecommendationContext` extended with `storeId`, `storeName`, a richer `products` shape (names/prices, not just active flags), `customerSummaries`, `inventorySnapshot`, `recentActivity`, and a minimal `blueprint` subset — all producers see the same symmetric input; `ruleBasedProducer` simply ignores what it doesn't use.
- `RecommendationItem.tsx`: the Layer 2 "✨ Ask Genesis" explain pill now only renders for `source === "rules"`.

**Architecture decisions**
- **Manual refresh only, cached indefinitely — an explicit user decision.** AI-generated recommendations persist across reloads (unlike Layer 2's fully ephemeral explanations) but never regenerate automatically; no background/cron regeneration was built (none exists anywhere in this codebase — see PH-02's Architecture decisions). Revisit once real usage patterns are known.
- **Rich context, with an explicit grounding guardrail — the user's core requirement for this phase.** The system prompt instructs Genesis to prioritize only the highest-impact opportunities grounded in the actual supplied data — typically 1–3, a 4th only if genuinely distinct and strong — and to return fewer (including zero) rather than invent generic advice when the data doesn't support a specific recommendation. Verified directly: a data-rich test store (Lunar Mothworks, 5 products, real order history) produced 3 specific, grounded recommendations (referencing actual product names, prices, and homepage copy); a thin test store (1 test product) produced 2 — neither padded to the schema's max of 4.
- **Deliberately a second `RecommendationProducer`, not a special case** — unlike Layer 2 (a transformation over already-decided output, correctly kept outside the producer pattern), Layer 3 genuinely proposes new, independent recommendations — exactly what `RecommendationProducer` was designed for since PH-05. `genesisProducer` itself stays pure (a DB read); the AI call lives entirely in the separate `generateGenesisRecommendations` service, triggered only by an explicit action, never from `produce()`.
- **The rule-based/Genesis boundary is held via prompt instruction, not shared live data** — the system prompt lists what the rule-based system already covers (unpublished store, zero products, no payment method, stale connections, recent failures, zero orders) so Genesis doesn't duplicate it, passed as static text rather than the rule-based producer's live output — preserves the "no producer sees another producer's output" purity rule while still avoiding redundant suggestions in practice.
- **`Store.blueprint`'s full `Blueprint` type couldn't be imported from `ai-actions.ts`** — a file with `"use server"` may only export async functions. `generateGenesisRecommendations.ts` instead defines a small local subset interface and reads `store.blueprint` as loosely-typed JSON, the same opaque-JSON-cast-at-read-site pattern `ai-actions.ts` itself already uses.
- **Mid-implementation refinements, all incorporated per explicit user feedback**: prompt language reframed from "generate up to 4" to "prioritize highest-impact, quality over count"; the full generated batch (not just a count) is recorded in `ExecutionLog.metadata` specifically so a future "don't repeat past suggestions" feature has real history to read — nothing reads this yet, this is architectural foresight only, not new logic; the trigger was renamed from "Refresh Genesis Suggestions" to "Ask Genesis to Review My Business" to read as a business-partner action rather than a generic data refresh.

Fixed by restarting the dev server process. Not a code bug, but worth noting: this class of failure won't show up in type-checking or direct function calls, only in the actually-running server.

**Database migrations**
- `add_generated_recommendations`: new `GeneratedRecommendation` table (`storeId`, `priority`, `message`, `actionLabel`, `actionHref`, `generatedAt`), indexed on `storeId`, cascade-deletes with `Store`. Purely additive, no existing-data risk. Hand-written (not `prisma migrate dev --create-only`, which fails non-interactively in this shell — same workaround as every prior phase's migration), applied via `prisma migrate deploy`.

**Breaking changes**
- None. `getRecommendations()`'s default producers array now includes `genesisProducer` alongside `ruleBasedProducer`, but a store with no `GeneratedRecommendation` rows yet (i.e., every store before this phase) simply sees zero genesis-sourced recommendations until the merchant clicks the new button — no change to existing rule-based behavior.

## PH-07, Layer 4 — Approval & Execution Framework
*2026-07-24 — Complete*

Fourth and final layer of PH-07: Genesis stops only advising and starts *acting*, under explicit owner approval. A generic framework, not a feature — per the user's explicit direction, any current or future Genesis capability plugs into the same `Recommendation → Approval Request → Execute → Verify → Record Result → Report Outcome` lifecycle, the same way `RecommendationProducer` let any recommendation source plug into `getRecommendations()` without a rewrite.

**What was built**
- New `ApprovalRequest` model — a generic approval gate, deliberately not recommendation-specific (`recommendationId` is a loose, optional reference, never required). Three statuses: `PENDING_APPROVAL`, `EXECUTED`, `REJECTED` — approving and executing collapse into one state since the approve flow is synchronous; the actual outcome quality lives on the linked `ExecutionLog` row via `executionId`, not duplicated here.
- `lib/execution/genesisActions.ts`: the `GENESIS_ACTIONS` registry — the plug-in point the user asked for. Any `Executable` becomes approvable by Genesis just by being registered here (an `Executable`, a Zod `inputSchema`, and a `getCurrentValues` function for the diff), with zero changes to the `Executable` contract itself.
- Two new `Executable`s proving the registry generalizes: `updateSeoExecutable` (`Store.blueprint.marketingAssets`) and `updateHeroExecutable` (`Store.blueprint.homepageContent`) — structural twins, each touching a different blueprint section with zero special-casing between them. Neither knows anything about `ApprovalRequest`, recommendations, or Genesis — ordinary Executables, callable via plain `execute()` from anywhere.
- `generateGenesisRecommendations.ts` extended with an optional, discriminated-union `proposedAction` on each recommendation. When present, the code (not the model) computes `previousValues` from the real, already-fetched blueprint data, validates the model's proposed `input` against the registered action's own Zod schema (defense in depth beyond the SDK-level union), and creates the `ApprovalRequest`.
- `approveGenesisAction`/`rejectGenesisAction` (`app/dashboard/ai-actions.ts`) — plain `redirect`-based Server Actions. Approve calls `execute()` with the registered `Executable`; reject only updates `ApprovalRequest.status`. Either outcome deletes the linked `GeneratedRecommendation` row — approved-and-applied or declined advice shouldn't keep showing.
- New dedicated **"Awaiting Your Approval"** dashboard section (`ApprovalRequestsPanel.tsx`), positioned between Attention and Recommendations — a deliberate UX decision, not folded into the existing Attention Panel (see Architecture decisions). Each item shows a summary plus a collapsible, generically-rendered Current → Proposed diff (`<details>`, one row per field key, driven by data shape not per-action JSX) before Approve/Reject.
- `ExecutionStatus` gained a `PARTIAL` value, framework-level, even though neither of this phase's two actions produces it — added now so a future multi-part action (e.g. "3 items, 2 succeeded") doesn't require a contract change later.

**Architecture decisions**
- **PH-03's `execute()` engine needed almost no changes.** The central finding from this phase's design research: `Executable`/`execute()` already implement "Execute → Verify → Record Result" completely — permission checks, `.verify()`, and the single append-only `ExecutionLog` write all already exist. The only genuinely new system this phase builds is the piece *before* execution: a persisted approval gate holding a proposed action until the owner explicitly says yes. The only engine-level change was adding the `PARTIAL` status; `execute()`'s permission-check, `executionId`, and `recordExecution()` logic are byte-for-byte unchanged.
- **A dedicated "Awaiting Your Approval" section, not folded into the Attention Panel** — explicit user reasoning: "something's broken," "something's waiting on your decision," and "here's what happened" are three different mental models, and blending them is cognitively messy.
- **`ApprovalRequest` is deliberately generic, not `RecommendationAction`** — explicit user instruction: *"Don't make this section specific to recommendations... later it'll hold marketing campaigns, product edits, homepage redesigns, social posts, inventory changes, booking changes."* A recommendation is only ever one possible originator of an `ApprovalRequest`, never a required one — nothing in the model, the registry, or `execute()` assumes one exists.
- **No `ExecutionLog` row is written at proposal or rejection time.** `ExecutionLog` represents things that were actually executed; a proposal awaiting a decision, or one that was declined, never was. This keeps `getStaleExecutions`' existing PENDING-row logic (PH-05) completely untouched — zero risk of a rejected proposal being misread as an abandoned execution.
- **No FK on `ApprovalRequest.recommendationId`** — a hard foreign key would risk an in-flight approval being cascade-deleted if the merchant clicks "Ask Genesis to Review My Business" again mid-review, replacing the `GeneratedRecommendation` batch underneath it.
- **A visible diff, not a blind Approve button** — explicit user reasoning: *"That reinforces that Genesis is proposing a specific change, not making mysterious edits behind the scenes."* `previousValues` is computed from real fetched store data, never from the model's own restatement of what it was shown — the diff is trustworthy by construction, not by asking the model to accurately quote itself.
- **Two concrete actions, not one** — the user's own reasoning for the second: *"If both work through the same execution engine without special cases, you'll know the architecture is holding up well."* Both are ordinary `editStoreExecutable`-shaped Executables (derive everything from `ctx.storeId`, no caller pre-fetch needed) — no new Executable pattern was introduced to support them.

**Bugs found and fixed during implementation**
- None during the initial build. The same stale-Prisma-Client-after-schema-change class of issue from Layer 3 was anticipated this time and avoided by restarting the dev server proactively after `prisma generate`, before verification began.

**A real bug found by the user's own post-ship usage, not by verification testing**: `generateGenesisRecommendations()` created a new `ApprovalRequest` for a `proposedAction` without first checking whether a `PENDING_APPROVAL` row already existed for that same `(storeId, actionType)`. Two "Ask Genesis to Review My Business" runs on the same store — one from this phase's own verification, one from the user testing the real dashboard — produced two independent `update_seo`/`update_hero` pairs instead of the second superseding the first, confirmed directly against the database (4 total `ApprovalRequest` rows from 2 generation runs 16 minutes apart). The only reason no duplicates were visibly stuck on the dashboard is that the user approved all four individually before reporting it — a normal user who ran "Review My Business" twice without immediately clearing every proposal would have accumulated duplicate pending approvals for the same action indefinitely. Fixed: before creating an `ApprovalRequest`, `deleteMany({storeId, actionType, status: "PENDING_APPROVAL"})` for that action type first — a fresh review supersedes any earlier still-pending proposal of the same type. Only `PENDING_APPROVAL` rows are ever touched; an already-`EXECUTED` or `REJECTED` row is resolved history and untouched, the same "don't rewrite the past" discipline as `ExecutionLog`. Verified with two consecutive generation runs on a test fixture: confirmed zero duplicate pending rows per action type after both runs, and confirmed run 1's original row ids were fully superseded (not just outnumbered) when run 2 re-proposed the same action types.

**Database migrations**
- `add_approval_requests`: new `ApprovalRequest` table, indexed on `(storeId, status)`, cascade-deletes with `Store`. Purely additive. Hand-written and applied via `prisma migrate deploy`, same workaround as every prior phase's migration.

**Breaking changes**
- None. `ExecutionStatus` gained a value (`PARTIAL`) that nothing currently produces; `STATUS_DOT`/`STATUS_LABEL`'s exhaustive `Record<ExecutionStatus, string>` typing forced both display maps to be updated as part of this change, which is exactly the safety net that typing exists for.

**Verification performed**
- `npx tsc --noEmit` / `npx eslint` clean on every touched/new file.
- Direct verification against the real Claude API and real store data (Lunar Mothworks — 5 products, real order history): confirmed Genesis produced two genuinely matching, well-grounded `proposedAction`s in one real run — an `update_seo` proposal (current SEO fields were genuinely empty, confirmed via a direct pre-check; proposed copy referenced real product terminology) and an `update_hero` proposal (referencing the store's actual $26.99 Starter Kit product by name and price). Confirmed `previousValues` on both `ApprovalRequest` rows exactly matched the store's real pre-generation blueprint data, proving it was computed from real data, not the model's restatement.

## Architecture Pivot, Phases 0–5 — "Genesis Operates the Business"
*2026-07-25 – 2026-07-26 — Complete*

A distinct roadmap from the PH-0X numbering above, started after PH-07 completed, governed by a north star crystallized mid-pivot: *"Genesis is the environment, not a feature. The owner's business occupies the central workspace. Genesis persistently surrounds that workspace, understands its state, communicates what matters, and acts within the authority the owner has granted it. As Genesis gains capabilities, complexity should move into Genesis rather than into the owner's interface."* Condensed here since these phases aren't yet individually written up in this file the way PH-0X is — see the fuller detail preserved in this session's own memory (`project_architecture_pivot_audit.md`) — Phase 6 below (Delegated Authority) gets the full treatment as it's the phase just closed.

- **Phase 0 — Authority/action classification foundation.** `GenesisActionCategory`/`AuthorizationTier` added to the `GENESIS_ACTIONS` registry, `ApprovalRequest.authorizationTier` snapshot column — inert scaffolding, zero behavior change, hardcoded `always_ask` everywhere.
- **Phase 1 — Closed the chat-vs-manual approval fork.** 4 new registered actions (`update_theme`, `update_brand_identity`, `update_store_identity`, `update_homepage_content`) plus rewiring chat's `update_hero`/`update_seo` writes through the same `ApprovalRequest` gate the proactive-review engine already used, closing a real duplication where chat and the recommendation engine wrote the same fields two different ways.
- **Phase 2 — Genesis Workspace v1.** Desktop sidebar replaced with a horizontal top tab bar (mobile bottom tabs unchanged); `GenesisAssistant`'s closed pill gained a real ambient state dot; `lib/dashboard/genesisState.ts`'s `deriveGenesisState` became the one shared priority computation instead of duplicated inline conditionals.
- **Phase 3 (3A/3B) — Website Workspace v2.** 3A: unified, consistently-styled presentation of Website proposals. 3B: `update_section_order` as Genesis's first structural action, previewed via the real storefront renderer (an owner-only `previewOrder` query param) rather than a second mock-rendering system.

Three triggers, all via `next/server`'s `after()` riding an existing request (Home load, chat-turn-end, Stripe webhook) — no scheduler/queue/worker anywhere. Real Purple ("opportunity")/Red ("urgent") Genesis Language states, backed by this model instead of "a recommendation row happens to exist."
- **Phase 5 — Measure/Learn.** `ApprovalRequest.topicKey` (stable business-issue identity, honestly nullable — never fabricated) and new `PostExecutionMeasurement` model: deterministic, zero-AI-cost before/after `Order` data for one executed action, with `concurrentActionTypes` preserving confounding context — deliberately never a causal/attribution claim, no percentage/lift/verdict field anywhere in the model. `recentGenesisHistory` feeds a bounded (≤5, ≤60 days) slice of past outcomes and rejections into `generateGenesisRecommendations`'s prompt, with rejection treated as context ("the owner may have declined the wording, not the idea") rather than permanent suppression.
- **Phase 6 — Delegated Authority.** See the dedicated entry immediately below.

## Architecture Pivot, Phase 6 — Delegated Authority
*2026-07-26 — Complete*

Lets Genesis handle a specific, narrow class of action without asking first, under bounded and immediately-revocable owner-granted authority — without collapsing Genesis's judgment, its authority, and the underlying permissions/execution/verification stack into one system. See `ARCHITECTURE.md`'s *Delegated Authority* section for the full architectural writeup; this entry covers what changed and how it was verified.

**What was built**
- `CATEGORY_MAX_TIER` (`lib/execution/genesisActions.ts`) — a hardcoded, non-owner-configurable ceiling per `GenesisActionCategory` (`content`→`auto`, `operations`→`always_ask`, `integration`→`auto_below_limit`, `communication`→`auto`, `money`/`destructive`→`always_ask`). `GenesisActionDefinition` gained a required `maxAuthorityTier` field per action, validated at module load against its category's ceiling. Of the 8 registered actions, only `update_seo` got `maxAuthorityTier: "auto"` — every other action, including `update_hero`, stays `always_ask`.
- New `DelegatedAuthority` model (`storeId` + `actionType`, unique, `revokedAt` nullable) — the smallest durable representation of an owner's grant. `ApprovalRequest` gained `decisionMode` (`"human"` | `"autonomous"`, frozen snapshot) and `delegatedAuthorityId` (which grant authorized an autonomous decision, snapshotted permanently).
- New `PERMISSIONS.AUTHORITY_MANAGE`, OWNER-only (never granted to EMPLOYEE) — governs granting/revoking authority, deliberately separate from `STORE_MANAGE`.
- New `lib/execution/genesisAutonomy.ts`: `tryExecuteAutonomousAction` (self-contained — re-validates the grant, the store owner's own permission, action eligibility, and input shape before ever calling `execute()`) plus `grantDelegatedAuthority`/`revokeDelegatedAuthority`. Wired into `generateGenesisRecommendations.ts`'s existing proposal loop; deliberately never reachable from chat.
- `execute()` (`lib/execution/engine.ts`) gained `opts.preAuthorizedGrantId` — the one way to skip `requireStorePermission`'s human-session requirement, independently re-validated (not trusted) by re-fetching the grant and resolving it through the `GENESIS_ACTIONS` registry to confirm, by object identity, that it matches the exact `Executable` being run.
- `revertApprovalRequest` (`ai-actions.ts`) — undo for any `EXECUTED` action, re-running the same `Executable` with the original's `previousValues`. Creates a new row rather than rewriting history; shipped in this same milestone rather than deferred, since autonomous execution skips the moment a human could otherwise have caught something first.
- `ActivityFeed` and the Marketing page's new "Recently handled" section both surface `decisionMode` distinctly ("Handled by Genesis automatically" vs. a human approval) without touching the append-only `ExecutionLog` row itself — joined at read time by `executionId`. `recentGenesisHistory` (Phase 5) also gained `decisionMode`, explicitly informational in the prompt: it never changes what Genesis is currently allowed to do.

**Architecture decisions**
- **Category ceilings are maximums, not defaults or grants** — `communication`'s ceiling was deliberately set to `auto` (not hard-locked) since Genesis may eventually handle routine customer communication, while high-risk communication actions would still individually declare `always_ask`; `integration`'s ceiling (`auto_below_limit`) is reserved the same way `AuthorizationTier` itself reserves that value ahead of any action having a real quantitative bound to check it against — no speculative limit machinery was built for it.
- **One lineage, not a parallel automation system** — an autonomous decision is an `ApprovalRequest` row like any other, distinguished only by `decisionMode`/`delegatedAuthorityId`. Verified retroactively correct: Phase 4/5's dedupe, measurement, and learning-context machinery needed zero changes to work correctly with autonomous decisions, since all of it keys off `status`/`decidedAt`/`topicKey`, agnostic to `decisionMode`.
- **Judgment, authority, and confidence/experience stay on separate code paths reading separate data** — Claude's reasoning (informed by Phase 5's history) never sees or influences the authority check; the authority check (a live `DelegatedAuthority` lookup) never reads measurement/history data. This is enforced structurally, not just by convention: the two computations have no shared data dependency that could let one leak into the other.

**A real architectural conflict found and resolved, not designed around**
- The original plan assumed a new `executeAutonomousAction` could call `execute()` directly, bypassing only the *wrapper* (`approveGenesisAction`)'s human-session requirement. Implementation revealed `execute()` **itself** unconditionally calls `requireStorePermission` whenever an `Executable` declares a `requiredPermission` — true of all 8 registered actions — meaning no Executable could run in a genuinely unattended context (an `after()` callback, a webhook) without an engine change. Resolved by adding `opts.preAuthorizedGrantId`, scoped tightly per explicit review: it doesn't trust a caller's claim, it re-fetches the exact grant and independently re-verifies it before ever skipping the human-session check.

**A real bug caught by live verification before it reached the end-to-end proof**
- The first implementation of `execute()`'s re-check compared `grant.actionType` (a `GENESIS_ACTIONS` registry key, e.g. `"update_seo"`) against `executable.action` (the low-level `ExecutionLog` action string, e.g. `"store.update_seo"`) — two different namespaces that are never equal. Every legitimate autonomous execution failed closed with "Delegated authority is missing, revoked, or does not match this action." Fixed by resolving `GENESIS_ACTIONS[grant.actionType].executable` and comparing the resulting object by identity instead of comparing strings — immune to the namespace mismatch, and to a caller separately asserting an actionType that doesn't actually describe what's being executed.

**Database migrations**
- `add_delegated_authority`: new `DelegatedAuthority` table (unique on `storeId`+`actionType`, cascades with `Store`), `ApprovalRequest.decisionMode`/`delegatedAuthorityId` columns. Purely additive.

**Breaking changes**
- None. `GenesisActionDefinition` gained a required `maxAuthorityTier` field, forcing all 8 existing registry entries to declare one explicitly — mechanical, no behavior change for any of the 7 that stayed `always_ask`.

**Verification performed**
- `npx tsc --noEmit` / `npx eslint` clean throughout, including after the `engine.ts` fix.
- Full authority-check matrix via direct calls against disposable test stores: no grant → declines, no row created; active grant → autonomous `EXECUTED`, real `Store.blueprint` change, correct `ExecutionLog` attribution (`actorType: "GENESIS"`); revoked grant → declines immediately; a manually-inserted grant for a hard-locked action (`update_hero`) → still refused (defense in depth); malformed input → declines cleanly.
- `execute()`'s `preAuthorizedGrantId` re-verification tested in isolation: a real, active `update_seo` grant used against the `update_hero` `Executable` → FAILED, zero write occurred; a revoked grant → FAILED; a bogus grant id → FAILED; a valid matching grant → SUCCESS with no human session at all.
- A real, live end-to-end run with two actual Claude calls: granted `update_seo` authority in advance, ran a genuine business review that produced both an `update_seo` proposal (auto-executed, real store data changed, no PENDING_APPROVAL row ever created) and an `update_hero` proposal (correctly stayed on the human-approval path, `decisionMode: "human"`) — proving Genesis's judgment and Genesis's authority operated as fully independent layers within one real review.
- The real Next.js server-action write path — grant, revoke, and revert — executed through actual HTTP requests replicating the exact rendered form encoding (including a bound-action's `$ACTION_REF_n`/`$ACTION_n:0`/`$ACTION_n:1` fields, not just a plain action), through a real authenticated session, no shortcuts: revert correctly restored the real store data and left the original decision row immutable.
- Confirmed `EMPLOYEE` structurally lacks `AUTHORITY_MANAGE` — cannot grant, revoke, or benefit from any delegation.
- All disposable test data cleaned up; dev server stopped after verification.

## Family Beta — Behavioral Tracking & Friction Instrumentation, incl. Welcome to Genesis
*2026-07-26/27 — Complete*

Instrumentation of the existing product for the first family beta round — the feature freeze declared right after the previous entry stayed in effect throughout; nothing here changes what Genesis does, only what gets durably recorded while testers use it. A read-only audit (three parallel passes over `ExecutionLog`/`StoreMessage`/`ApprovalRequest`/`GenesisObservation`/Business Journey/auth-session state, the `StoreDraft`→generation→`confirmStoreDraft` flow, and the nav/shell instrumentation surface) found zero telemetry/analytics infrastructure anywhere in the codebase — no middleware, no analytics package, no timing instrumentation, no session-instance concept — so this phase adds the smallest durable layer to close that gap, plus three small "Welcome to Genesis" UX changes the same audit surfaced as necessary for the creation flow to actually be the only walkthrough a new user needs.

**What was built**
- **One new model, `ProductEvent`** (`prisma/schema.prisma`) — a generic, append-only instrumentation table, deliberately not several bespoke tables, following this codebase's existing convention (`EXECUTION_ACTIONS`) of a plain, freely-growing string catalog rather than a Prisma enum for `name`/`category`. `attemptKey` is always a real, already-meaningful identity (`topicKey`, `groupId`, `dedupeKey`, a `storeDraftId`, or a fixed flow name like `"stripe_connect:{storeId}"`) rather than an invented counter — an attempt sequence is reconstructed by ordering rows sharing one `attemptKey`, never by a stored "attempt number." `metadata` only ever holds small allow-listed fields and *references* to other rows' own ids (an `ApprovalRequest.id`, a `StoreMessage.id`) — never raw chat/form content, which stays in its own real row and is joined at reconstruction time.
- **`lib/telemetry/events.ts`** — `logProductEvent` (the one writer every call site uses; swallows its own failures so a telemetry write can never break the real feature it's attached to) and `findLikelyRephraseOf`, a deliberately simple, deterministic "likely rephrase" heuristic: normalized word-overlap (Jaccard) between a new user chat message and the immediately preceding same-role message within a 10-minute window — no embeddings, no AI call, always surfaced as "likely," never asserted as fact.
- **Session-instance correlation** — `auth.ts`'s `jwt` callback mints a `sessionInstanceId` (random UUID) only on a real sign-in (the same `if (user)` branch that already sets `token.id`), threaded to `session.user.sessionInstanceId` via the session callback. Groups "one sitting" for a small trusted beta cohort without building real session infrastructure — persists for the JWT's lifetime (30 days), a stated, accepted tradeoff for this beta round, not a per-tab boundary.
- **Instrumented, by call site**: navigation (`nav.section_view`) and `?focus=` outcome (`focus.route_resolved`/`route_unresolved`, including the previously-invisible "this badge's link didn't resolve to anything" case) in `DashboardShell.tsx`; real server-side chat-turn duration plus the rephrase flag (`chat.turn_completed`) in both `applyGenesisMessage`/`applyGenesisMessageToStore`; approval decisions (`approval.approved`/`rejected`/`reverted`/`approve_failed`/`revert_failed`) in `approveGenesisAction`/`rejectGenesisAction`/`revertApprovalRequest`; Stripe/PayPal connect attempts (`integration.connect_attempt`) in `app/dashboard/actions.ts`; opt-in perceived-loading duration (`perf.action_pending`) added to the shared `SubmitButton.tsx` (new `trackPerf` prop, `undefined` by default so every existing call site — including the public storefront's own checkout/newsletter buttons, which share this component — is byte-for-byte unchanged) and wired into the Payments page's connect/recheck buttons; the full "Welcome to Genesis" creation journey (`creation.started`/`regenerated_via_form`/`confirmed`) in `generateStoreDraft`/`confirmStoreDraft`, all sharing one `attemptKey` (the draft's own id) end to end.
- **`journey.stage_reached`** — Business Journey's own stage logic (previously inline in `BusinessJourney.tsx`, 100% derived with zero persisted history) extracted, behavior-preserving, into a new shared `lib/dashboard/journeyStage.ts` (`deriveJourneyStage`), so a real stage *transition* becomes a durable event without a second, competing journey model. `logJourneyStageIfChanged` reads the last stage event for the store first so an unchanged stage never re-logs on every Home load; called from an `after()` callback in `app/dashboard/page.tsx` so it never adds latency to the page it's derived from.
- **Three small "Welcome to Genesis" UX changes**, per the same audit's finding that the existing `StoreDraft` → chat → generation pipeline already satisfies "answers flow through real generation" but reads as a form-first experience rather than a conversation: the first screen's copy/heading changed from "Create your store" to "Welcome to Genesis"; `GenesisAssistant` gained an optional `defaultOpen` prop, set on the draft-review page so chat is open by default instead of an easy-to-miss collapsed pill; the mini "regenerate from these fields" form — a real, previously-undetected bypass of the conversational/diff-tracked chat path (it calls `generateStoreDraft` directly, writing no `StoreDraftMessage`, no diff, no `recordGenesisExecution`) — was relabeled "Start over from scratch," moved into a closed-by-default `<details>` near the bottom of the page, and reframed as a rare escape hatch rather than the primary refinement mechanism.

**A real bug found and fixed during live verification, not assumed away**
`ProductEvent.storeDraftId` was initially a real foreign-key relation to `StoreDraft` with `onDelete: Cascade`, mirroring `ExecutionLog`'s own `storeDraftId` pattern. But `confirmStoreDraft` deletes the `StoreDraft` row as the normal, successful *last step* of the creation journey — not an edge case — which meant every `creation.*` event for that journey was silently destroyed the moment a tester actually finished onboarding, and the terminal `creation.confirmed` event (written *after* that delete) would have failed to insert at all under a real FK. Caught by a live disposable-account walkthrough that found the events missing post-confirmation. A follow-up migration drops the now-incorrect FK constraint without touching the column or any existing data. Re-verified with a second disposable account: all four `creation.*` events (including `creation.confirmed`) now correctly survive the draft's deletion, correlated under one `attemptKey`.

**Database migrations**
- `add_product_event`: new `ProductEvent` table, 4 indexes (`userId+createdAt`, `sessionInstanceId+createdAt`, `attemptKey`, `storeId+createdAt`), FKs to `User`/`Store` (cascade — neither is routinely deleted the way a `StoreDraft` is) and, at this point, an FK to `StoreDraft` (cascade).

**Breaking changes**

## Beta 1 — Upload Reliability Fix
*2026-08-06 — Resolved*

Two independent real users (Sean and a family member) hit the same production bug: a chat photo upload would appear to start, never complete, and fall back to a generic "the connection may have dropped" message. Root cause was two distinct, stacked limits on request body size — found and fixed as two separate commits, because the first fix, while correct, wasn't sufficient on its own and re-verification with a real (not synthetic) photo caught the second.

**What was found**
- **Layer 1 — Next.js Server Actions' own default.** `next.config.ts` had never configured `experimental.serverActions.bodySizeLimit`, so it silently capped every Server Action request body at 1MB, while `lib/businessAssets/uploadAssetFile.ts` allowed uploads up to 8MB. Any real phone photo (routinely 2-8MB) threw a 413 that Next surfaced as a generic 500. Confirmed via a live production repro plus the actual Vercel runtime log line (`Error: Body exceeded 1 MB limit`), not code inspection.
- **Layer 2 — Vercel's own platform-level Serverless Function payload ceiling.** After raising the Server Actions limit to 10mb and confirming small synthetic files worked, a real 5.52MB iPhone photo (iPhone 14 Pro Max, real EXIF/GPS) still failed with a 413. The Vercel runtime log for that request showed `"source":"static"` with no function invocation at all — rejected at Vercel's own routing layer before Next.js code ever ran. This ceiling isn't configurable from application code.

**What was built**
- `next.config.ts`: `experimental.serverActions.bodySizeLimit: "10mb"` (necessary, not sufficient on its own — see Layer 2).
- The real fix: moved the byte transfer itself client-side. `app/api/blob/business-asset-upload/route.ts` (new) issues short-lived Vercel Blob client tokens via `@vercel/blob/client`'s `handleUpload`, with the same `GENESIS_CHAT` permission gate `uploadBusinessAssetFromChat` already enforced, now run *before* any byte moves rather than after. `GenesisAssistant.tsx`'s upload handler now calls `@vercel/blob/client`'s `upload()` directly, PUTting the file straight to Blob storage from the browser — the file's actual bytes never touch this app's own serverless function, so neither size ceiling applies regardless of photo size. `uploadBusinessAssetFromChat` (`app/dashboard/ai-actions.ts`) now receives only the resulting Blob URL and metadata, a payload of a few hundred bytes regardless of the original file's size. `lib/businessAssets/uploadAssetFile.ts` lost its server-side `put()` call entirely (replaced by `finalizeUploadedAssetFile`, metadata-only validation) — its only caller, `ingestBusinessAsset`, updated to match.

**Breaking changes**
- None. Single call site for the changed functions (`ingestBusinessAsset`), confirmed via grep before refactoring.

**Verification performed**

- After the Layer 1 fix: re-ran the same repro (success), then a real valid ~2.2MB JPEG (generated with `sharp`, not random bytes) to confirm the full pipeline — Blob write, Server Action return, chat message creation, and a genuine (non-canned) Anthropic vision response correctly identifying the deliberately-random test image as visual noise.
